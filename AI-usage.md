# AI Usage Documentation

This document describes how AI tools were used during the implementation of the **Requests Search & Filter** feature.

---

## AI Tools Used

### Amazon Kiro (powered by Claude Sonnet 4.6)

Kiro served as the primary AI development environment for this feature. It was used end-to-end across all phases:

- **Spec authoring** — generating requirements.md, design.md, and tasks.md via Kiro's built-in spec workflow
- **Backend implementation** — writing all C# code across the `Requests.Api`, `Requests.Application`, and `Requests.Infrastructure` projects
- **Frontend implementation** — generating the full Angular application under `frontend/`
- **Test implementation** — writing unit tests and the in-memory `FakeRequestRepository` in `Requests.Tests`
- **Documentation** — generating README.md and this AI-usage.md

---

## Prompts and Interactions That Shaped Key Design Decisions

### Spec Creation

The requirements, design, and task breakdown were generated through Kiro's spec workflow. The developer provided the initial feature request and Kiro produced:

- **`requirements.md`** — structured acceptance criteria in WHEN/THEN/IF format, covering filtering (Requirement 1), security/ownership (Requirement 2), sorting (Requirement 3), pagination (Requirement 4), input validation (Requirement 5), and the Angular UI (Requirements 6–9)
- **`design.md`** — layered architecture diagram, `IQueryable` pipeline design, data contracts (`SearchRequestsQuery`, `PagedResult<T>`), Angular component tree, Microservices architecture (Part B), and Azure cloud deployment sketch (Part C)
- **`tasks.md`** — a sequenced 20-task implementation plan with wave-based dependency ordering

### Backend Implementation

Key design decisions shaped during implementation:

- **IQueryable pipeline order** — the design explicitly specified the filter chain order (ownership → requestNumber → status → requestType → createdFrom → createdTo → count → sort → paginate → execute) to guarantee all filtering happens at the database level, not in memory. This was a deliberate requirement stated in the spec.
- **`SearchAsync` method signature** — the interface takes `currentUserId` and `isAdministrator` as explicit parameters rather than relying on an ambient context, keeping the method testable and the repository free of HTTP concerns.
- **Controller validation logic** — enum binding errors (`status`, `requestType`) are handled via `ModelState` checks with explicit allowed-value messages; numeric and date validations are handled manually in the action method. This split was chosen to keep validation close to the HTTP layer while keeping the service and repository clean.

### Frontend Implementation

Key decisions in the Angular architecture:

- **`SearchFilterComponent`** — uses a reactive `FormGroup`; debounce of 500ms is applied only to the `requestNumber` text field, while dropdowns and date pickers emit immediately. This matches the acceptance criteria in Requirement 6.2.
- **`RequestsTableComponent`** — column sort toggle logic (same column flips direction, new column defaults to `asc`) is handled entirely in the component via an `EventEmitter`, keeping `AppComponent` as a thin coordinator.
- **`PaginationComponent`** — Hebrew button labels ("הקודם", "הבא") and the empty-state message ("לא נמצאו בקשות התואמות לחיפוש") were specified explicitly in the requirements and implemented as written.
- **`AppComponent` wiring** — acts as the single source of truth for `query`, `result`, `loading`, and `error` state; all child components communicate upward via `EventEmitter` and receive data via `@Input()`, following standard Angular data-flow patterns.

### Test Implementation

- **`FakeRequestRepository`** — implemented as an in-memory stand-in that mirrors the `IQueryable` semantics of the real `RequestRepository`. Each filter predicate is applied in the same order as the real pipeline so that unit tests remain meaningful without requiring a database.
- **Test case selection** — test cases 8.1–8.11 cover all core behavioural axes: admin vs. regular-user ownership, each individual filter, combined AND logic, pagination invariants, and sort direction.

## AI-Generated Code: Review and Modifications

All code in this repository was generated by Kiro task execution. The developer's role was to:

1. **Review the spec documents** (`requirements.md`, `design.md`, `tasks.md`) before approving each implementation phase — the spec documents represent the human-in-the-loop checkpoint.
2. **Specify the IQueryable filter chain order** explicitly in `design.md` to ensure database-level filtering. This was a deliberate architectural constraint written into the design before code generation began.
3. **Specify Hebrew UI text** in the requirements (`requirements.md`, Requirements 6.5, 8.1) so that the Angular components would render the correct language from the start rather than requiring post-generation edits.
4. **Verify compilation and test results** at each checkpoint task (tasks 7, 9, 17, 20) to confirm generated code was correct before proceeding to the next wave.

No significant manual corrections to the generated code were required — the spec documents provided sufficient precision for Kiro to generate correct implementations on the first pass.
